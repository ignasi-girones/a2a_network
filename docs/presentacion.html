Agent Discovery

Los agentes se encuentran y se registran automáticamente

Agente se inicia → Publica Agent Card → Se registra en el Orchestrador
Orchestrador consulta Registry → Lee skills de cada agente → Planifica el debate

El orquestador no sabe de antemano qué agentes existen. Lee sus skills y decide cómo usarlos.

Comunicación A2A

JSON-RPC 2.0

Protocolo de transporte estándar

  • SendMessage — síncrono
  • SendStreamingMessage — SSE

Task Lifecycle

Cada petición crea un Task con estados:

submitted working completed

El orquestador usa streaming hacia el frontend (progreso en tiempo real) y llamadas síncronas a los workers (espera respuesta completa).

Nuestro caso de uso

Una deliberación multi-agente donde agentes con distintos roles debaten un tema y buscan consenso.

¿Por qué debates?

  • Explota la naturaleza distribuida de A2A
  • Cada agente es independiente con su propio LLM
  • El consenso emerge de la interacción, no de un solo modelo

¿Qué lo hace interesante?

  • Distintos modelos = distintas perspectivas
  • El orquestador no sabe la respuesta
  • Agentes externos pueden unirse en vivo

Lo que decide el LLM

  • Qué skills usar y en qué orden
  • Qué roles asignar a cada agente
  • Cuándo extender el debate
  • Si añadir agentes nuevos

Lo que está hardcodeado

  • Métricas de consenso (embeddings)
  • Umbral de convergencia (0.75)
  • Máximo de rondas de extensión (3)
  • Pesos de los componentes del score

Consenso empírico

Sin opinión del LLM — solo matemáticas

Eje AE1 ↔ AE2

Las aperturas de AE1 y AE2 definen posición 0.0 y 1.0. Cada texto posterior se ubica por similitud coseno con esos anclas.

4 componentes

  • Dispersión (40%) — qué tan cerca están
  • Similitud (35%) — semántica entre textos
  • Movimiento (15%) — ¿se están moviendo?
  • Concesiones (10%) — "tienes razón"

Fórmula del score

score = 0.40 · dispersión
     + 0.35 · similitud
     + 0.15 · movimiento
     + 0.10 · concesiones

Si score ≥ 0.75 → consenso

Adición dinámica de agentes

La potencia real del protocolo A2A aplicada a nuestro caso de uso

Ronda 1

AE1, AE2 y AE3 debaten. No llegan a consenso.

El orquestador detecta agentes disponibles en el registry que no están participando.

Ronda 2

El planner decide: "Un experto legal ayudaría a desbloquear esto."

AE4 se incorpora al debate con contexto completo de lo discutido.

El agente añadido puede ser de otro equipo, otra organización, otro país.
Solo necesita publicar una Agent Card con skill "debate".

Filtrado inteligente

Solo agentes con skill debate. Nunca normalizer, feedback ni herramientas.

Decisión del LLM

El planner decide si la expertise del nuevo agente ayuda al deadlock actual.

Catch-up automático

El nuevo agente recibe todo el contexto previo via depends_on.

Hoy cada framework de agentes es un silo. LangChain no habla con CrewAI ni con AutoGen.

Respaldo de la industria

Google, Salesforce, SAP, Atlassian, MongoDB y más de 50 empresas detrás.

Diseño pragmático

Donde A2A puede ser diferencial

🏥  Empresa

Un agente de RRHH de SAP negocia vacaciones con un agente de planning de Jira. Cada empresa mantiene su agente, A2A los conecta.

💰  Marketplaces de agentes

Publicar agentes especializados como servicios. Descubrimiento automático por skills. Economía de agentes.

🏗️  Cadenas de valor

Agente de un proveedor coordina con agente de logística de otra empresa para optimizar entregas en tiempo real.

🧪  Investigación

Agentes de distintos laboratorios analizan un mismo dataset desde perspectivas diferentes y consolidan hallazgos.

Retos y preguntas abiertas

Confianza y seguridad

¿Cómo confías en un agente que no conoces? Autenticación, autorización, sandboxing de acciones.

Observabilidad a escala

Con decenas de agentes interactuando, el debugging se vuelve exponencialmente difícil. Necesitamos tracing distribuido nativo.

Competencia con MCP

Model Context Protocol (Anthropic) resuelve parte del problema. ¿Convivencia o guerra de estándares?

Nuestra perspectiva

MCP conecta modelos con herramientas. A2A conecta agentes entre sí. Son complementarios, no competidores.

A2A + MCP = el stack completo

No compiten — cada uno resuelve una capa distinta

MCP (Anthropic) A2A (Google)
Conecta Modelo ↔ Herramientas Agente ↔ Agente
Analogía USB para un dispositivo HTTP entre servidores
Ejemplo Agente accede a base de datos Dos agentes negocian un contrato
Scope Dentro de un agente Entre agentes independientes

En nuestro proyecto usamos ambos: MCP para que los agentes accedan a herramientas, A2A para que se comuniquen entre ellos.

Lo que hemos aprendido

🤔

El consenso es difícil

Los LLMs tienden al "ambos tienen razón". Forzar convergencia real requiere prompt engineering agresivo.

⚡

Rate limits everywhere

Con 4+ agentes en paralelo, los TPM de los proveedores se agotan rápido. La diversidad de modelos ayuda.

📊

Métricas > opinión

Medir consenso con embeddings es más fiable que pedirle al LLM que se autoevalúe.
